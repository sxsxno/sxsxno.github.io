2026腾讯游戏安全技术竞赛-PC客户端安全-个人题解

发表于 2026-11-04

2026 腾讯游戏安全技术竞赛 · PC 客户端安全 · 决赛

赛题把「影子组织」的控制中枢「根」摆在面前：一个 shadow_panel.exe 要求输入 16 字节的终止密码，而它真正的校验逻辑根本不在用户态，甚至不在驱动里——只有先让程序把机器虚拟化掉，才能看到那段代码。

六个评分点其实就是一条完整的攻击链：怎么装上去 → 装上去做了什么 → 怎么检测 → 怎么拿到密码 → 怎么在别的机器上也算出来。下面按这条顺序记录。

# 要求 分值
1 找到部署条件，成功运行 shadow_panel.exe 进入密码终端 0.5
2 分析对操作系统底层攻击、隐藏核心代码的完整实现 2.5
3 编写检测代码，检测该攻击手法 2.0
4 计算出终止密码 1.0
5 编写 keygen，任意机器任意一次运行都能算出密码 2.5
6 完整解题过程与源码 1.5

环境：VMware 里的 Windows 10 1909（开启嵌套虚拟化 / VT-x），IDA Pro、VMware debug stub + gdb、Python 3。

1 让它跑起来：部署条件

直接双击 shadow_panel.exe 是进不到密码输入框的，要么闪退，要么什么都不发生。先静态看启动流程，它被拆成清晰的四个 Phase。

Phase 0：Hyper-V + IOMMU 检测（sub_144A07540）

  1. CPUID(1) → 检查 ECX 的 bit 31（Hypervisor Present）；
  2. CPUID(0x40000000) → 校验 Hypervisor vendor 是否为 "Microsoft Hv"；
  3. IOMMU：通过 NtQuerySystemInformation（类 76）查询 ACPI 固件表，检查是否存在 Intel VT-d 的 DMAR 表（签名 0x52414D44）或 AMD-Vi 的 IVRS 表（签名 0x53525649）。

三者缺一不可，这就是为什么在很多机器上它「装不上」。

Phase 1：VHD 路径准备（sub_144A075F0）

准备 VHD 部署路径 C:\Windows\Temp\WdiServiceHost\，并清理残留的旧文件。目录名看起来像是 Windows 自带的诊断服务，属于很典型的白利用路径选择。

Phase 2：驱动部署（sub_144A07620 → sub_144A05540）

  1. 先执行 CPUID(0xDEADBEEF, 0x114514)，若 EAX == 0x01919810 说明 hypervisor 已经活跃，直接跳过部署；
  2. 生成随机服务名，拼接出 xxx.sys 的路径；
  3. CreateFileW → WriteFile（驱动 blob 来自 .data 段的 unk_145CCA010）→ CloseHandle，先把内嵌驱动释放到磁盘；
  4. 通过 .tvm0 段中的代码创建、挂载 VHD 并部署驱动；
  5. OpenSCManagerW → 清理服务 → DeleteFileW，把痕迹擦掉。

VHD 容器在这里的作用是绕过驱动签名强制（DSE）：驱动不是从普通目录直接加载的，而是通过虚拟磁盘挂载点间接加载。

Phase 3：Hypervisor 激活验证（sub_144A07650）

再发一次 CPUID(0xDEADBEEF, 0x114514)，确认 EAX == 0x01919810（十进制 26318864），才认为 HyperCharge hypervisor 安装并激活成功。

结论：机器需要支持 IOMMU，并且开启了 Hyper-V；用管理员权限启动 shadow_panel.exe 即可进入密码输入终端。

顺带一提，0x114514、0x1919810、0xDEADBEEF、0xB16B00B5 这组 leaf/subleaf 明显是出题人的恶趣味，但正是这组「魔法数」成了后面所有题目的入口。

2 它到底做了什么：底层攻击与代码隐藏

题目在内嵌的资源里放了一个 .sys。程序初始化时把它重命名为一个随机字符串再加载，所以第一次跑完之后，磁盘上根本找不到原始文件名。

驱动本体受到 TVM 保护。

.tvm0 段里的逻辑被虚拟化得很深，一条指令要经过解释器走十几步，硬逆基本不现实。于是换个角度：不逆代码，先看它调了哪些 API，把行为序列 dump 出来。

序列里有很明显的「申请物理内存 + 进行 mapping」的组合，联想到程序强制要求开启 Hyper-V，再加上调试时能确认 .exe 侧的校验是通过 CPUID 指令完成的（它的通信封装 sub_144A12290 就是个裸 cpuid，把 leaf、subleaf、两个 64 位参数分别塞进 EAX/ECX/EBX/EDX），基本可以判断这是一套 VT-x 的 hypervisor rootkit。

这一步我有用 AI 辅助分析，把 CPUID 包装函数和周围的 CFF 混淆理了一遍，确认数据流。

我的猜测是：驱动把一段 VMX 代码页映射到 EPT 中操作系统「看不见」的区域。要验证这个猜测，静态分析已经没用了，只能上调试器。

先用 VMware 的 debug stub 连上虚拟机，取到进程内存基址。

然后在用户态程序执行 cpuid 之前下断点。

单步执行，程序就跳进了一段全新的代码——这段代码在 IDA 里查不到，也不属于任何已加载模块。

里面能看到 vmresume、vmlaunch 这些指令，确认走的就是 Hyper-V/VT-x 那一层。

至此整条链路可以实锤了：

  1. 程序运行后加载一个隐藏的驱动；
  2. 驱动申请物理内存，并把代码映射到操作系统不可见的区域；
  3. 所有 VMX 指令在运行时由驱动动态生成，所以即使拿到完整驱动二进制，反汇编器里也搜不到任何 VMX 指令；
  4. 最后由程序执行 CPUID 触发 VM-Exit，真正的校验逻辑在 hypervisor 层完成。

这种「把自己插到 OS 和硬件之间、让原系统变成 Guest」的手法，就是教科书里的 Blue Pill。区别在于这里不是教科书上的简单版：它做了 EPT 代码隐藏、动态指令生成、TVM 虚拟化三重保护。

3 检测代码：怎么发现这台机器被「插」了一针

检测思路其实第一条题已经给了：程序每次启动都会先执行 CPUID(0xDEADBEEF, 0x114514)，若 EAX == 0x01919810 就认为 hypervisor 已活跃、跳过部署。

那我主动发同样的请求就行了——返回 0x01919810，说明这台机器的 VMX 代码已经被注入了。

4 终止密码：进到 VMX 里去看

既然（2）里已经能用 debug stub 单步进到隐藏代码，那拿密码就是顺水推舟——进到 VMX 实际执行的代码段，一路跟到 subleaf 的分发逻辑。

分发进去之后就是校验密码的代码。

这里有两种做法，调试党可以偷懒，逆向党可以硬啃：

  • 调试：直接在 cpuid 前后读 r8、r9，就能拿到本次期望的密钥/中间值，拼起来就是密码；
  • 逆向：key 来自 [page+0x500] 和 [page+0x508]，把校验算法还原出来。

5 Keygen：换个机器也得能算出来

第 4 题的做法有个致命前提：得能读那个 page。而一旦程序进入 VT 环境，那个页基本就读不到了——你没法在自己被虚拟化的同时去读 host 侧的内存，所以密钥拿不到。

那就只剩两条路：

  1. 逆驱动，搞清 [page+0x500] / [page+0x508] 到底是怎么写进去的；
  2. 找出密钥的生成规律，自己算。

先试第一条。调试一段时间后发现，VMX 代码是由 sub_14000FC40 处的代码动态生成的，这也能解释为什么驱动本体里一条 VMX 指令都搜不到。但这一段虚拟化程度太深，大部分逻辑最终会跑到 .tvm0 段执行，逆起来极其痛苦。

6 小结

这题的设计很有意思，六个评分点其实是一个连贯的叙事，而不是六个孤立的小问：

  • 它必须先在你的机器上「成功」，才有后面的攻击；而「成功」的条件（IOMMU + Hyper-V）本身就是一道情报题；
  • 它的核心代码不在任何可静态分析的二进制里——既在 TVM 保护的段里，又在运行时才生成的 VMX 代码里，静态分析到这里彻底失效；
  • 它的通信协议是公开的：CPUID 成了唯一的突破口，既能用来检测（第 3 题），也能用来爆破（第 5 题）；
  • 密钥空间被自己的实现压小了：两个 qword 里只有一个在变，而且只变两个字节，于是「逆向不出来的算法」可以直接交给 hypervisor 当 oracle。

几个踩过的坑：

  1. 驱动里搜不到任何 VMX 指令，一开始以为分析错了方向，后来才明白是运行时补丁（sub_14000FC40）；
  2. cpuid 在用户态无法任意控制 EBX，必须走 shellcode，否则要么编译不过，要么结果被覆盖；
  3. 进入 VT 环境之后就别想再读 host 侧的内存了，第 4 题能偷懒读寄存器，第 5 题必须老老实实枚举。
